# Facebook Reddit Telegram 运营恢复与节奏控制方案

日期：2026 年 11 月 11 日。状态：用户已确认设计，并授权细化实施计划；尚未授权产品实施或上线。

目标是让已获授权、具备执行条件的工作持续推进；需要等待时，能说明依据、影响范围和恢复条件。采用规则与明确反馈驱动的节奏控制，先积累真实样本，后续另行设计自适应调整。

本轮交付设计文档、需求记录和[实施计划](../plans/2026-11-11-channel-recovery-evidence-cadence.md)。不修改线上，不调整账号、额度、授权、服务、数据库或社媒内容，也不创建生产发布请求。用户确认设计仅表示可以据此细化实施计划；不自动构成生产切换授权。

## 一 已确认的方向与方案选择

用户已选择先做规则与反馈驱动，积累真实样本后再考虑自适应调整。当前不以另一组固定日次数替换原来的低额度，也不启用此前提出的入群每天 2 次、回复每天 6 次和统一间隔 30 分钟。

| 方案 | 行为与取舍 | 本次决定 |
| --- | --- | --- |
| 规则与反馈驱动 | 根据有效授权、群规、明确冷却、重复动作、执行故障和资源条件判断；决定可解释、可重放 | 采用 |
| 同时加入自适应节奏 | 根据足够的真实执行样本调整频率；需要额外处理样本偏差、误判和效果评价 | 留到后续 |

本方案沿用现有账号环境、持久任务、动作账本、后台排期和发布流程。工程实现复用哪些模块、如何优化查询由实施者决定，但必须满足下述行为和验收条件。涉及新的用户授权、平台能力或数据处理用途时，仍须单独取得相应授权。

## 三 统一的执行判断

每项工作按以下顺序判断：当前账号和授权是否有效；是否已有未确认的同一外部动作；目标和动作是否允许；证据是否完整且仍有效；是否处于适用的冷却、工程退避或资源等待；最后才领取执行位。网页、群资料或模型输出不能自行扩大授权。

| 工作状态 | 用户看到的含义 | 下一步 |
| --- | --- | --- |
| 可执行 | 条件已满足，正在排队或执行 | 按队列推进 |
| 到时恢复 | 有明确时间，例如反馈中的冷却期限、用户工作时间或工程退避 | 保存时间，到期重验条件 |
| 条件变化后恢复 | 登录、授权、规则、目标或运行配置缺失 | 等待对应事件，避免反复重跑同一步 |
| 待核对外部结果 | 操作可能已提交，尚无确定回执 | 只核对原动作，不重发 |
| 已结束 | 成功、跳过、明确失败或不再适用 | 保存具体业务结果；新证据需要时创建后继任务 |

一次等待必须记录原因、证据引用、适用的账号／目标／动作、触发时间、规则版本、恢复时间或恢复事件。没有明确恢复时间时显示“条件变化后重查”，不编造倒计时。多个限制同时存在时保留全部限制，不能因其中一个到期就忽略其他限制。

## 四 按证据控制节奏

### 4.1 什么可以成为依据

| 依据 | 生效范围 | 恢复方式 |
| --- | --- | --- |
| 平台明确反馈及可验证的冷却期限 | 按反馈确定为动作、群或账号范围；无法确定时不缩小解释 | 到期后重新核验；失效登录和受限状态另行处理 |
| 当前群规则和已核实的目标条件 | 对应群、目标和动作 | 群规更新、重新取得完整证据或目标条件变化 |
| 用户明确设置的工作时间、暂停、额度和预算 | 用户指定的范围 | 按原设置恢复；系统不自行放宽 |
| 重复动作、已处理的问题、未确认回执 | 同一操作或存在冲突的范围 | 去重结束，或取得确定回执 |
| 临时连接故障、查询超时、资源不足 | 对应来源、执行通道或受影响节点 | 使用已登记的有限退避，释放资源后重试 |
| 确定性错误，如适配器不支持、输入不合法 | 对应任务或能力 | 修复能力或输入后重试；时间流逝本身不构成恢复依据 |

平台反馈必须保留原始类型和来源。未能解析的异常不能自动归类为“平台限流”。工程退避、节点容量和任务运行上限属于工程保护，须与平台限制及用户业务额度分开显示。

### 4.2 移除缺少依据的共用日额度

入群、回复和搜索分别安排，不再共享“今天执行过一次就全部停止”的系统默认日额度。正常执行没有统一的产品默认日次数目标，也不以凑足次数为目的；仍受实际授权、平台与目标规则、明确用户限额、预算和执行容量约束。

实施前先追溯每个现有限额及冷却参数的来源。能够确认只是旧代码默认值的，迁移到新规则；用户明确设置或已作为授权条件接受的限制继续生效。来源无法确定时仅保留受影响范围的限制并提出一项合并说明，不能默默扩大权限。原有搜索 30 分钟冷却、回复间隔等也必须经过同一来源审查，不能只移除每日次数、却保留无法解释的定时等待。

本次不设置新的入群或回复频率数字。没有平台期限时也不安排无间断循环：同一账号页面串行，一次只领取一项外部操作；只响应新的合格机会或到期事件。异常重复由操作唯一性、未确认回执、已有资源预算和有界恢复机制控制。工程保护参数沿用适用且已登记的运行配置，实施计划须列出其来源、数值和边界测试；缺失或不适用的参数先完成隔离验证，不能伪称平台规则后直接启用。

### 4.3 决定等待多久

同一项操作的多个已知时间限制取最晚恢复时间；还存在非时间条件时，到期也不能直接提交。明确的反馈期限不能被随机抖动提前。临时工程故障复用现有有界退避，并记录它是工程参数；确定性错误则等待条件变化。

发生单群问题时仅阻止该群对应动作，其他合格目标继续推进。账号级反馈才影响该账号；节点资源问题按实际共享资源范围等待，不能以一个渠道的故障暂停整个项目。外部提交范围不明时保守阻止可能冲突的范围，不能未经核实就缩小到单群。

### 4.4 何时唤醒

使用现有持久排期等待最早相关期限，账号恢复、授权变化、规则更新、新机会或资源释放可提前唤醒重验。事件重复和进程重启不会重复领取动作。

处理顺序优先保障原动作回执，其次处理仍有效的待答问题和已合格候选，再补充研究。不同渠道独立排队；在现有公平调度基础上防止研究长期饿死。心跳、结果核对和平台状态检查可以继续，但不能每轮都把全部历史任务和候选重新扫描。

## 五 三个渠道分别怎么恢复

### 5.1 Facebook

将“登录已连接”“有运营授权”“有执行归属”“有可用目标”分别核对。保留账号现有关闭状态，直到通过明确的运营启用入口取得本账号授权；修复不会把登录动作变成发布授权。

授权接入后，为 Facebook 登记适用的独立筹备和渠道任务，不能只修改自动运营开关。已有页面／管理目标能力与普通成员参与能力必须分开；现有代码仅支持的目标类型才能进入执行，不把 Reddit 普通成员能力直接套到 Facebook 群。

缺少外部来源或平台放行时，展示缺少什么、由用户还是平台维护方处理。业务资料整理、内部选题和不依赖受限读取的草稿可以继续；不能制造已核验社区机会或真实外发成绩。

验收：启用只影响指定账号；缺条件时给出可处理事项；已有有效条件的工作会生成持久任务；暂停、换号和撤权能阻止旧任务提交。

### 5.2 Reddit

保留独立研究和分发计时。来源访问许可、用户托管授权、目标规则和平台放行分别核验，不用“账号已经连接”替代任何一项。

将无需受限外部读取的准备工作与来源研究入口分开。尚无来源许可时可整理已有业务资料和内部草稿，但不能使用未经允许的新来源访问，也不能将内部草稿标为适合某个未核验社区的稿件。

针对加锁超时，先在隔离环境重现“一个渠道执行历史回访或慢查询、另一个渠道需要推进”的情形，记录实际阻塞方。将历史扫描和耗时计算移出项目控制锁，优化已定位的查询，最后在短事务中核对账号、授权和任务版本。真实点击仍保留必要的提交屏障；不能为减少等待而删除暂停、撤权、去重保护，也不先用扩大超时掩盖问题。

验收：Telegram 存在慢任务时 Reddit 的独立筹备仍能完成；锁故障有界恢复且不会重复生成；来源许可未满足时不外读；没有合格目标时不发布。

### 5.3 Telegram

先分别修复两个已复现的判定错误。简介是否有实质内容应支持中文等不依赖空格分词的语言，并保留主题与受众核验。已经实际读取且内容完整的置顶，不因简介仍引用置顶而被再次判为未读；无法读取的外部条款、附件、页数缺口继续保持待核验。

对备用置顶读取记录具体失败阶段，至少区分身份或群变化、接口未取得完整列表、超时、正文不可读、附件或外部条款未覆盖。是否需要分页和持久续读由这些证据决定。验收必须覆盖现有前台和备用两条路径，而非单独提高条数。

候选按“发现元数据、规则与主题核验、可参与、已申请／已入群、可回复、已确认回复”推进，单个候选通过后即可交给参与队列，不依赖全批搜索完成。旧记录保持原样，新证据通过后继记录关联；证据不足则保存具体缺口和恢复条件。

答疑内容范围保持当前有效授权。本次节奏改造不自动从严格 FAQ 切换到宽松或语义答疑，也不启用主动发帖、推广、私信或离群动作。FAQ 模式是否另行调整独立决定，避免把内容能力变化混进节奏验证。

验收：入群不会消耗回复额度；同一问题不会重复答；有未知回执时不重发；不可执行的群不妨碍其他群；不存在合格问题时允许零回复。

## 六 内部记录与工作台呈现

工作台只需让用户读懂三件事：最近实际做了什么、当前卡在哪里、下一步何时或在什么条件下发生。正常合格工作无需逐条请求用户批准；仅缺少用户才能补齐的权限、登录或材料时汇总提示。

每项节奏决定的内部记录至少包括任务和操作标识、账号绑定版本、目标、动作、规则版本、证据类型及引用、触发时间、限制范围、恢复时间或事件、最终处置。记录尽量使用现有任务结果和关联记录；如果确需修改数据库结构，应单独列出迁移范围和回退方法，不能夹带实施。

业务结果分别统计内部产物、合格机会、确认入群、确认回复、待回执、跳过、受阻和失败。确认回复须有外部消息标识；点击和转化依原测量证据单独统计，未接通显示未知。保留“先成功入群、后因无问题跳过回复”的两个事实，不能只用最终跳过覆盖入群成果。

## 七 迁移和交付顺序

| 阶段 | 交付内容 | 前进条件 |
| --- | --- | --- |
| 设计审阅 | 本方案及需求记录 | 用户确认方案后才细化实施计划；线上仍不改变 |
| 根因与用例 | 锁阻塞复现、置顶失败分支、已复现判定缺陷和限额来源清单 | 需要改动的每个根因都有相应证据或失败用例 |
| 独立修复 | 按故障分别准备代码、设备适配和直接消费者验证 | 不捆绑无关改造；应用和专用执行器分别核对 |
| 节奏与渠道接入 | 新规则、旧默认值迁移方案、渠道登记和状态呈现 | 明确哪些默认值被替换、哪些用户约束保留；隔离验证通过 |
| 生产交付准备 | 正常 PR、范围匹配的检查、候选版本、兼容与回退记录 | 若之后获准交付，严格执行当时主线发布流程；本轮不执行 |
| 获准后的真实观察 | 先验证版本和动作回执，再积累业务样本 | 每个动作仍通过当时有效授权；没有真实机会时记录零机会 |

旧任务仅因原系统默认日额度而等待、且确定没有外部提交的，在切换时生成受新策略核验的后继任务；不篡改旧结果、不批量重放。存在未知提交的原任务继续原回执路径。换号、撤权和业务配置变化要求重新取得适用证据。

通用应用与 Telegram 专用执行器分别固定版本、校验摘要并独立回读。混合版本必须可识别；能力不一致时，仅停止受影响的外部操作并显示版本不匹配，不能静默回落到旧的共用日额度。兼容表和切换顺序在实施计划中根据最终产物冻结。

异常回退只阻止新操作，保留所有已提交动作和未决回执。恢复旧应用或旧执行器前先核对兼容性；不能仅因新代码回退就重发、删除任务或恢复过期授权。同步更新工作台运营流程图的单一内容源及相关排障记录。

## 八 验收清单

以下均为实施后的必验场景，不是本轮已通过的结果。

| 场景 | 必须看到的结果 |
| --- | --- |
| 有合格机会且无适用限制 | 进入排队和执行，不因旧产品默认“今天已执行过一次”停止 |
| 当天已经入群，随后有合格问题 | 回复独立判断；同一群、同一问题仍防重复 |
| 用户明确设置额度或工作时段 | 按原约束等待；到期后重验；系统不自动提高 |
| 平台明确给出冷却期限 | 在正确范围保存期限，不提前重试，不影响无关渠道 |
| 页面错误无法判定为限流 | 显示原故障或工程退避，不冒称平台要求 |
| 登录失效、撤权、暂停、换号 | 旧任务不能提交；恢复后重新核验，不强制重放 |
| 已提交但结果未知、服务重启、事件重复 | 只核对原动作；同一操作最终最多提交一次 |
| 完整中文简介、完整置顶仍被引用 | 不因英文空格或引用提示误拒；完整性和主题核验仍有效 |
| 多页置顶、附件和外部条款 | 能辨认完整与缺口；失败有具体阶段；未读完整不能伪报通过 |
| 单群或单来源失败 | 在该范围退避，其他合格工作继续 |
| Telegram 历史查询变慢 | Reddit 独立筹备能完成；最终提交的暂停和撤权保护仍成立 |
| Facebook 连接、启用和授权分离 | 连接不自动发布；获准后登记正确账号的工作；不影响其他账号 |
| Reddit 来源或目标不满足 | 继续适用的内部准备，外部读取和发布维持对应门槛 |
| 搜索没有合格结果或群里没有可答问题 | 明确记录零机会；没有虚构回复、点击或转化 |
| 版本不一致与回退 | 仅阻止不兼容操作，保留原账本和回执，不静默恢复旧日额度 |

采用现有 PostgreSQL、持久工作流和受控浏览器测试方式，先覆盖失败路径再验证修复。平台页面和账号用合成样本；真实业务观察不做批量真实提交故障注入。本地判定断言和模拟浏览器成功不能替代平台实号验收。

## 九 真实样本如何积累

将样本按渠道、账号、目标、动作和规则版本划分，记录从合格机会到执行的等待时间、阻塞原因与持续时间、确认动作、未知回执、重复尝试、内部产物及可验证的点击／转化。另记录无机会和未执行原因，避免只保留成功样本。

统计决策证据类型、误拒样本、工程退避占比、目标读取完整率和跨渠道等待。优先保存标识、时间、计数和受控证据引用，不新增全量聊天留存，不把账号资料、凭据和私有设备源码写入公开仓库。

第一阶段只收集和分析，不自动据成功率或增长效果调整频率。后续是否进入自适应设计，以故障和回执可解释、样本覆盖正常与受阻场景、测量可靠为前提，另行确认目标、样本充分性和调整边界；运行了若干小时或完成若干轮不等于样本已经充分。
