## 2. 交付目标和范围

目标体验保持：对话介绍业务 → Agent 引导补充必要事实 → 专属环境登录与授权 → 免费启动 → 默认自主运营 → 查看真实获客结果。

普通用户不配置模型、提示词、代理、CDP、线程或任务编排，不每日启动或逐条批准帖子。代理、环境、额度和监控由平台管理。必要的登录、身份核验与授权范围变更才进入用户流程。

首轮收尾不新增完整虚拟操作系统、广告充值/购买、无限制私信、原创视频制作或插件市场。已确认范围内的能力做实；新增写操作另列范围，不能默认已有授权。

## 5. 执行顺序与里程碑

### S1：补齐无需社媒登录的软件闭环

顺序：T01 → N01/N02 → R01 → P01 → U01；在外部条件等待时推进 A01、F01、L01 和各平台公开条件/测试材料准备。

通过标准：完整混合测试可运行、有明确判定器；环境/出口由平台管理；恢复不止停留在隔离目录；生产版本可安装和检查；对话主路径没有技术表单或每日手动启动。

当前受控长期测试继续运行并保留证据。扩展覆盖后的完整 72 小时测试使用新的测试版本和起点，不能把旧测试已运行的时长拼成完整混合验收。

R01 首版先完成单运行节点的安全灾备切换。不能证明旧控制者已停止或隔离时，拒绝激活新写实例；不在本轮提前建设自动多节点调度或无证据自动抢占。

### S2：生产环境、出口和灾备真正通过

顺序：P02 → N03 与 R02；P01 的安装和检查代码不等这些资源才开始写。

通过标准：实际在线节点、真实身份服务、三个固定出口、活动 Profile 加密磁盘、异地备份和独立密钥均核验；断开出口、节点重启及恢复保护正确；原方案目标为数据库 RPO ≤15 分钟、Profile RPO ≤24 小时、RTO ≤4 小时，须在目标规模测量后才标通过。

### S3：逐平台真实闭环与获客接入

按各平台条件逐个执行 C00/C01–C11，不要求等待全部平台就绪才开始首批试运营。W01 随首个可用渠道接真实网站。初估每平台 1–3 工程日只是调试假设；账号状态、地区、页面差异及适用条件可能改变工作量，首个平台完成后更新估算。

通过标准：每一个对用户开放的目标/格式都有真实证据；正常排期不依赖聊天指令或逐条审批；有效访问和转化有可追溯来源。获客提升需要真实样本，不能用测试发布或合成点击保证效果。

### S4：冻结候选版本，完成耐久和免费额度决策

在完整运行器、目标节点及首批真实闭环就绪后，执行不少于 72 小时的混合负载。运行器层用受控目标覆盖故障；渠道层按已授权范围单独保留试运营记录，不在真实账号上做破坏性故障注入。其余渠道的校准不因该测试暂停。

通过标准：无重复外部提交和越权；三个环境真实重叠；一环境等待/失败/接管不让其他环境整体停工；预热后资源趋势、队列公平与异常恢复满足测试前登记的标准。基础 API P95 <500ms 是原方案待验证目标，外部模型/浏览器等待分开测量。不能跑满时间后不检查资源趋势就验收。

结合 A02/F01 给出实际能力、限制、免费范围和容量结论。测试中途改动了关键执行/恢复路径，相关连续观察须按影响重跑，不把旧报告套到新版本。

## 6. T01 必测矩阵

| 场景 | 必须得到的结果 |
|---|---|
| 三环境同时执行文字、图文和视频任务 | 原生操作区间重叠，任务/素材/记忆不串；实际完成上传，不能只检查文件已入库 |
| A 等模型响应、暂停或处于接管 | B/C 继续执行；A 的旧版本输入和提交被拒；接管断线后不自动继续半完成页面 |
| 提交前崩溃、点击后确认丢失、重复事件 | 已发生的动作只核对，外部重复提交为零；重启后保持同一业务意图 |
| 数据库/网关临时失联、服务升级重启 | 任务和记忆可恢复，不依赖用户重新发消息；账本与权限继续有效 |
| 登录失效、验证页、页面布局变化 | 停止不确定写操作，明确必要处理；平台故障不伪装成发布成功 |
| 上游出口断开、身份或地区漂移 | 不直连、不借用其他出口；失败范围限于受影响环境 |
| 容量饱和与长时间循环 | 可观测排队和公平性；记录预热后内存、CPU、文件句柄、磁盘及进程数量趋势 |
| 测试计时结束 | 自动生成场景结果和资源分析；缺少覆盖、样本或证据时不能宣布完整验收通过 |

测试前固定负载版本、预算、目标硬件、容量与资源判定阈值。无外部重复提交、无越权和无双控制者是硬门槛，不能用平均成功率掩盖。
