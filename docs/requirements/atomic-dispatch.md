# 运营 Agent 工作拆分与并行调度设计

范围是单个业务 Agent 从接收目标到衡量结果的工作，以及会与它争用资源的手动操作。以下是目标设计，当前代码尚未按这些单元派发。基础设施备份、租户管理、计费后台和产品 UI 属于平台运维。

## 工作目录

每个编号代表可独立领取的一种工作。运行实例还须绑定具体对象和版本，例如一条来源、一份稿件、一个目标或一个实验窗口。箭头表示同一对象的直接依赖，分号隔开的分支可分别触发。已有且仍有效的产物可直接满足依赖。

| 工作域 | 拆出的动作与完成产物 | 触发条件与交接点 |
|---|---|---|
| 对话与控制 | A1 解释一条指令，产出意图；A2 应用一次开始、暂停或恢复，更新控制版本；A3 保存目标或偏好版本；A4 提取一份业务资料；A5 确认业务资料版本；A6 返回指令处理结果 | A1 按意图触发 A2、A3 或 A4。需要用户确认的资料由确认事件触发 A5。按消息顺序处理相互覆盖的指令。 |

## 实施目标与现状

目标有三项。独立工作能同时推进；互相冲突的工作有序执行；某个资源不可用时，其影响止于真实依赖该资源的任务。可验证的进展条件是：任务已到期、前置产物齐备、权限有效、所需资源有空位且执行服务健康。数据库或整机不可用属于系统故障，进入恢复流程。所有时间和吞吐指标以下述基线及验收为准。

现在 SupervisorWorkflow 等待一次 autonomous_cycle 返回，operating_kernel.cycle 从排序后的候选取第一项。私信扫描还可能在已选工作前执行。finish 将整份 operating_kernel 快照回写 Agent；心跳按 Agent 查最近的检查点。直接并发调用 cycle 会产生快照覆盖、归错心跳及重复选择风险。另有独立聊天、发布和分析工作流。迁移以当前业务任务和回执为锚点。

## 一、执行架构与数据边界

一个业务 Agent 持有目标、授权和计划。PostgreSQL 保存可恢复的调度状态；Temporal 承担唤醒、计时、投递和执行。沿用 lead.tasks 作为业务记录。建议增加调度实例、前置产物引用、资源占用三类关系，复用现有 outbox、模型预留账本、外部动作意图和回执。新增表采用现有租户隔离、Agent 作用域和数据库迁移机制。

| 对象 | 落地要求 |
|---|---|
| 动作目录 | 每类声明触发条件、输入输出、执行函数、依赖资源、幂等键规则、超时与恢复方式。一个业务动作可复用现有处理函数。K1–K6 是调度内部操作，避免递归生成“领取任务”的任务。 |
| 调度实例 | 唯一键由租户、Agent、动作、对象及业务意图组成；周期观测带窗口，草稿带资料版本。保存业务任务 ID、计划和实验引用、控制版本、状态、到期时间、等待原因、尝试号、租约代数及结果引用。外部写入键跨重试、配置升级和新旧入口保持稳定。 |
| 产物与依赖 | 链接、群证据、稿件、回执绑定对象、版本和有效期限。登记实例时验证动作依赖无环。后续回访生成带新窗口的实例；前置任务终止时明确取消、重算或转人工，防止永久悬挂。 |
| 投递与领取 | 完成、产物、后继事件同事务写入。事件允许重复投递，按实例键消重。调度器短事务、小批量领取，使用行锁跳过其他领取者；按固定顺序尝试取得全部执行资源，失败立即释放。对就绪和到期任务建分区条件索引，按各资源类别取候选，避免只扫描被热门资源占满的队头。 |
| 运行与展示 | 心跳、超时、进度、完成均按实例和租约代数更新。过期执行器的写回必须失败。Agent 总览从实例聚合，历史经营计划继续关联原业务任务。移除并行路径对整份 Agent 调度快照的覆盖写入。 |

## 二、一次调度如何进行

1. 消息、候选入库、稿件完成、回执到期、额度变更或资源释放触发一次合并唤醒；另按最近到期时间设定定时器。定期扫描漏送事件和失效租约，作为恢复路径。
2. 校验租户、运行状态、目标范围、配置版本及依赖。把仍缺产物、尚未到期或等待人工操作的实例登记为等待，并注明解除条件。从已满足条件的任务中按现有经营计划、业务评分和就绪等待时长排序。
3. 在机器总容量和每个 Agent 公平份额内，领取多个资源相容的实例。控制指令、已提交动作的回执和到期交付有执行机会；各类别轮转，等待时间提高优先级。限制每轮领取量，持续被跳过的就绪实例触发告警。
4. 提交领取事务后通过 outbox 派发。执行器开始时核对实例、代数与权限，耗时的网络访问、模型调用、浏览器操作均在调度事务之外完成。需要下一类资源时先保存本步产物、释放已持有资源，再让后继领取。
5. 结局为成功、等待、可重试失败、终止或外部结果待核对。临时故障按对象和错误类型退避并加抖动；达到重试上限后记录原因及恢复入口。暂停停止领取新业务动作，已有外部意图按既有权限保留待核对记录。恢复或改目标时只重算仍有效的工作。

## 三、资源与额度隔离

| 资源 | 调度规则 | 耗尽时继续推进的例子 |
|---|---|---|
| 模型调用和 token | 调度排序可参考成本；硬额度仅在确实调用模型前由现有 model.reserve 路径以请求实际输入的估算预留，沿用同一账本和结算。模型调用完成后释放并发位，结算或按原规则保留不确定用量。实验已配置的限制仅作用于对应请求。 | 公开读取、去重、已发消息回读、埋点入账和无需模型的报表继续。若同一工作含读取和模型判断，先交付读取产物。 |
| 登录页面 | 按真实浏览器 Actor／会话互斥，手动、聊天、自动入口共享约束。只有使用物理隔离会话时才可跨会话并行。执行器租约失效后须确认旧浏览器操作已退出或隔离旧会话再重用。 | 登录页面繁忙时，独立公开页面及后台模型任务继续。 |
| 公开页面与来源 | 独立只读上下文，设并发上限及每来源冷却。按候选有效库存高低水位补货，失败来源退避。 | 来源 A 遇到限流时，来源 B 与已入库候选继续。 |
| 素材与机器容量 | 渲染单列限并发；监测 CPU、可用内存、事件循环延迟和数据库连接。压力持续时先降低可选研究和渲染，保留控制与恢复能力。 | 长渲染期间，暂停指令和到期回执可得到执行位。 |
| 平台写入 | 账户和目标频率沿用既有策略。按业务意图去重，临提交复核权限、目标和消息版本。 | 等待群 A 审批期间，账号可执行其他已到期且获授权的工作。 |

额度处理须覆盖四个边界。① 模型额度为零的任务保存输入并释放所有执行位。② 两个请求争用最后一份额度，仅成功预留者发起调用，另一项等待。③ 预留释放、额度上调、新计量周期或对应实验额度变化时，只唤醒受影响的任务并重新估算。单次请求若超过完整周期上限，应显示需要缩小输入或调整配置，避免每天空转。④ 无每日上限模式沿用其原有语义，仍受服务限流与机器容量约束。实施时查实际 Agent 配置，禁止仅凭代码默认值设置生产限额。

## 四、外部写入与故障恢复

提交入群、发帖、私信、修改资料等操作先持久化意图、稳定业务键和回读基线。提交边界再次检查控制版本和资源所有权。平台返回确认时保存回执；超时或进程退出后转为与原意图绑定的回读。仅在平台支持同一幂等键，或证据明确证明未提交且现有策略允许时重新发送。无法区分成功与否时保留待核对状态。目标范围内的冲突动作等待，其余目标继续。

执行器退出后可重做纯读取；模型请求结果不明时复用已有调用标识、缓存和不确定结算记录，避免双重预留；渲染产物按版本核验后复用。外部操作、持久化结果和数据库事务分别处理，避免把执行器重试当作平台写入的成功凭证。

## 五、交付阶段与切换条件

| 阶段 | 实施内容及代码入口 | 进入下一阶段的门槛 |
|---|---|---|
| 0 基线 | 按目录对齐实际入口、旧任务状态和必要权限。采集一个完整运营周期的工作量、耗时、队列年龄、资源占用、额度推迟原因及重复动作。记录测试拓扑和实际实例配置。 | 78 个编号均有执行入口、内部操作或停用条件说明；可重放一组固定负载；低频路径补充合成场景。 |
| 1 持久化与影子计算 | 在数据库迁移、operating_kernel、workflows、worker 增加实例、索引、幂等投递、租约和按实例心跳。旧入口继续执行，新路径只计算可并行集合。同步把私信扫描、实验上下文和计划引用显式绑定到实例。 | 相同输入下能解释旧选择与新集合的差异。影子模式没有平台写入、付费调用或真实资源占用；重放、双领取和租户隔离测试通过。 |
| 2 独立后台工作 | 接入 C/D 的公开读取、G 的内容和素材、I 的测量及 J 的离线判断，保留既有分析摄取入口，A/K 的控制和恢复优先接通。按实际步骤替换整类 token 准入。 | 零额度、慢模型、慢来源和长渲染均通过隔离验收；对同一负载观察到不同类任务实际重叠，独立任务排队时间下降。 |
| 3 登录态读取 | 接入 B/D/E/F/H 的身份、原生检索、观察、私信读取、受众与回执。复用 Actor 锁并验证跨进程及人工接管。 | 同一页面无交叉导航；审批和定时回访释放执行位；重启后优先核对原意图。 |

| 5 扩容及收敛 | 单个试点 Agent 从两个不争用资源的执行位起步，每次只提高一个资源上限。覆盖混合负载和至少一个额度周期，再扩大范围。 | 达到效率指标，容量有余量，无安全不变量违例。保留按动作回切能力，观察旧在途任务清空后再移除旧选择逻辑。 |

切换以 Agent 和动作族为单位，持久化派发所有者与切换代数。旧在途任务由原入口收尾，新任务由新入口领取。故障时先关闭该族新领取，核对在途租约、意图和回执，再把未领取实例交回旧路径；对结果未知的写入保留唯一核对入口。数据库采用增量迁移，回切后旧版本仍可读原业务任务。Temporal 的在途工作流通过版本分支或新工作流类型迁移，并执行历史重放测试。

## 六、验收与运营观察

下列时间数值是试点建议门槛，阶段 0 记录基线后冻结测试条件。正确性门槛全程生效。效率评价使用同机器、同配额、同任务混合及可比外部响应；分别统计资源已就绪与资源确实饱和的任务。

| 注入条件 | 必须观察到的结果 |
|---|---|
| 模型额度为零、实验额度先耗尽、供应商限流 | 仅依赖相应资源者等待，无数据库事务、账号锁或执行位被占住。将公开读取、回执和采集分别送入，仍能完成。额度恢复后原实例继续，无重复模型预留。 |
| 一个公开读取或渲染人为延长 60 秒 | 资源空闲的独立任务在慢任务结束前启动并完成；低速定位到对应来源或资源。 |
| 同时提交两个超出剩余额度总和的请求 | 账本无超额预留，失败者没有发起付费调用；结算后按实际余量唤醒。 |
| 持续涌入候选并夹入回执、私信和下游交付 | 高水位触发减速，低水位恢复。队列最老年龄可解释；可执行的回执及交付在持续探索负载下仍有进展。 |
| 重复投递、双执行器领取、完成前后宕机、旧租约迟到 | 一个业务键只有一个有效后继，旧代数不能覆盖新结果。同一登录页无并发操作，未知外部结果回读，重复外部提交为零。 |
| 暂停、改目标、撤销授权、人工接管、新旧调度切换 | 已落地控制版本后，旧版本无法开始新的受控提交。先前可能已经抵达平台的请求保留核对记录，其他租户及 Agent 不受影响。 |
| 漏唤醒、数据库短时中断、执行服务重启 | 恢复扫描重建到期工作；无丢失实例，无永久占用。所有等待实例都有唤醒来源、截止复查或明确人工处理原因。 |
