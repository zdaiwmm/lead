# 家庭 Linux 节点发布适配

在独立分支 home/systemd-release-adapter 从 PR #1 的 cca372e0561909eaed5cd3747d86384ac1d1d681 接入既有 systemd 和备份流程。节点出站取单。验收覆盖进程实际挂载、混合版本、回退、重复请求与只读线上检查。用户授权隔离演练和线上只读检查，实际切换、服务重启、迁移须另行确认目标环境和完整 SHA。

范围为 lead 应用进程。共享的 Chamber 覆盖、持久数据库、任务账本、配置和账号资料由原节点保留。线上未知版本和未归档覆盖必须先核对。恢复仅切回兼容旧应用。需要数据库或依赖变更的版本进入单独演练。

## 验收记录

- Mac 上的 Compose 目录仅对应本地 PostgreSQL 和 Temporal。家庭 Linux 节点通过 systemd path / target 启动，运行 API、Web、数据库和 collector。PC 上的只读绑定显示 API 和 Web 使用 Chamber 工作台覆盖，专用执行器另有模块覆盖。线上实例的单一 lead Git SHA 暂不可证。
- 历史 PC 导出中能对照的 134 个 API 包文件与 d96b7483 一致。main 在此之上另有一个整理提交，四个 API 文件有差异。历史 API 局部发布回执指向 6c1a17c9。后续执行器四个模块的回执摘要均可在已推送的 Chamber 相关分支历史中找到。实际进程字节的完整归档仍待维护者读取。可审阅并在节点以有权限的身份运行 scripts/home_code_inventory.py，在节点内逐项比对。脚本只读实际进程命名空间中的代码，打印模块名和摘要，不生成备份。
- 既有 Python 发布器支持包交换、API 重启和失败还原。整站候选使用独立只读镜像和 systemd 绑定，复用本地备份与隔离恢复验证单元。首次纳管前要先归档共享覆盖，并解决当前缺少专用 lead Worker 与持久 Temporal 的问题。
- 临时目录回归 10 项通过。另在 PC 普通用户的临时 systemd 单元中用合成进程验证切换、注入健康失败后回退，并由真实 PID 工作目录核验两个版本；持久化测试文件保持一致。未在生产挂载、数据库或社媒账号上做故障注入。
- 线上只读 current、verify 6c1a17c9… 与 verify d96b7483… 均退出 1，原因是共享 Chamber 挂载。账户无法读取所有进程根目录，线上代码清单仍不完整。PC 可直接出站访问 GitHub API，接入时还需要节点专用低权限身份、gh、单节点调度、可审计的维护锁与合成工作流回执。
- 继续交接时先完成只读盘点、代码归档与 lead / Chamber 归属确认。另行确认生产目标和完整应用 SHA 后方可实施首次主机纳管或切换。

## 后续无人值守准备

PC 普通账户的独立交接目录已直接从 GitHub 获取裸仓库，并验证 Ubuntu 软件包摘要、解包 gh。生产执行身份和回报权限需独立配置。后续增加节点内的只限代码归档、CI 构建与验摘要的镜像准备、数据库维护锁、按 worker 启动独立验收的 Temporal 工作流。真实临时 PostgreSQL 验证了锁的竞争、写阻塞、锁丢失及有在途任务时的拒绝；在独立 Temporal 容器中完成合成工作流，重启该测试容器后从独立客户端回读历史，错误 SHA 被拒绝。节点专属密钥和实际主机配置均留在节点。线上仍处于共享布局，真实基线归档和生产切换未执行。
