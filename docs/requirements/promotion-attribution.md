# 推广访问归因实施方案

## 业务规则

工作台「获客效果」仅展示当前 Agent 推广带来的流量。推广点击只来自通过现有过滤的短链跳转。到站 PV、访客和有效访问按本次访问的推广入口统计。网站像素仍记录直接访问，后台可按全站与未归因分组核账。全站 UV 以匿名设备独立去重，同一设备可同时出现在多个渠道。

同一标签页内，有效推广入口开启一次推广访问。同源页面导航、刷新和 SPA 路由在会话有效期内沿用该来源。无推广参数的新外部入口、地址栏直访、超时后活动开启新会话。独立标签页各自管理访问，匿名设备标识沿用。缺少同源导航证据的新文档采用未归因。服务端继续验证短链签名、网站、Agent、有效期，兼容现有经过校验的旧推广码。测试环境单独统计。

注册、线索与订单沿用现有最近有效触点及该触点冻结的归因窗口。直接回访可以产生一笔有证据的延迟转化，但回访本身计入未归因流量。服务端转化按业务去重和可信级别统计。

## 实施与历史数据

1. SDK 按标签页和访问入口隔离会话与推广凭证，保留重试队列中事件发生时的证据。旧 SDK 的缓存不导入新会话。
2. 服务端入库先验证点击有效期。浏览流量按访问会话确定来源，转化按已验证触点或点击确定来源。推广视图、趋势、渠道、地区、人数、金额使用同一个筛选条件。面板、获客明细、事件明细一律展示推广数据。全站分组供后台对账。
3. 报表 worker 用已有的按日队列和事务，从源回执重建旧版日汇总、小时汇总和去重集合。旧 SDK 曾缓存并重复上报推广来源。历史回执能区分本次会话与过往转化触点时，按本次会话重算。旧会话保存了推广码而缺少当次导航证据时，无法区分真正的推广落地和旧缓存重放，保留其原会话来源。旧快照在推广数字重算期间显示待汇总。原始回执、订单和匿名身份保留。
4. 在隔离 PostgreSQL 与 SDK 测试中核对下表，再构建工作台。在 GitHub 推送完整候选提交，通过该提交的 CI 后准备家庭节点的发布包。

| 验收场景 | 推广统计 | 全站统计 |
| --- | --- | --- |
| 新设备首次访问裸网址 | 点击 0，PV 0，设备 0 | PV 1，设备 1 |
| 该设备随后从短链进入，站内再浏览一页 | 点击 1，PV 2，设备 1 | 累计 PV 3，设备 1 |
| 同标签页或新标签页再次从地址栏进入 | 推广 PV 与设备数不增加 | PV 增加 |
| 直接回访完成注册或支付 | 按有效触点、冻结窗口和业务去重核算转化 | 业务事件照常记录 |
| 无触点、失效凭证、其他 Agent 或测试会话 | 排除对应推广成绩 | 按原有校验规则接收或拒绝 |
| 旧汇总、重复任务、进程中断 | 重算完成后显示同一结果 | 已接收的事实可重新核对 |
