验收条件如下：

- 各组收集完整测试集合，再按文件唯一分组。汇总证明各组原始收集一致、执行并集完整、没有遗漏或额外重复。

## 实现与交接

采用四组固定矩阵 `backend-tests` 和单一 `backend` 汇总。曾考虑同一 runner 使用 pytest 并发进程；固定端口、全局数据库与报告文件要求先隔离环境，因此选择独立 runner。按文件 SHA-256 取模分组，完整保留文件内执行顺序和模块夹具。前三个提前检查文件明确归第 0 组。

跨组文件间的原始全局串行顺序不再保留；原来依赖完整串行运行暴露的跨文件污染，需要受控 Linux CI 验证。提前检查到本组完整执行的顺序保留。新增测试、文件和参数自动进入收集证明，不维护一份容易遗漏的测试白名单。

所有组继续等待前端同轮已验证浏览器包，不改变构建位置。部分文件混合数据库、浏览器和工作流用例，且存在跨文件夹具导入；当前没有足够证据证明某组完全不依赖浏览器，因此不提前启动所谓“纯后端组”。后续可依据完整计时与依赖证据再拆。

分工以稳定边界安排。主负责人负责工作流、现有交付测试、计时和本记录。独立只读核验确认发布消费者使用精确 job 名称。实施代理仅负责 pytest 分组报告、汇总校验和其行为测试；不修改工作流、业务代码或其他任务目录。没有额外模型或供应商覆盖。

`scripts/ci_pytest.py` 的 JSON 以完整 node ID 的 SHA-256 标识用例，仅保留源码文件及去掉参数的测试名。`scripts/ci_backend_proof.py` 在同轮收集的五份报告上核对四组完整执行与一份明确提前检查。完整逐项报告保留七天，失败时也上传；原始 JUnit 不上传。

新脚本和测试未加入工具范围白名单，因此本变更选择应用完整验证。没有降低首次验证范围，也没有改动发布消费者。后续获准合入时，在精确 main 的正常完整验证中测量实际关键路径、各组排队、准备、执行、清理和产物汇总时间；还须核对 GitHub 上的 `backend` 汇总与 `Application verification`，不能以本地测试替代。
