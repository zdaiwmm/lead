## 关键方案

比较两种形状：

1. 仅增加 prompt、空判断重试或定时唤醒。没有确定性来源校验，不能证明等待成立，且会放大空搜索循环，不采用。
2. 在现有命令、任务和实验边界表达具体来源，提交时重新核对当前 canonical 状态，采用此方案。运行状态各有一处持久真相，不创建另一套调度器。

经营内核在上下文提供 `continuation_sources`。模型 continuation 可引用 `source_ref: {kind: task|experiment|resource, id, version}`，服务器在准入后重新核对。结果提供 `continuation_check`，视图投影为 `continuation.check`，区分真实 waiting、具体 blocked 和 missing。停止探测的资源不是自动唤醒生产者。历史无校验信息的等待不能被显示成新契约已验证。

用户指令复用 `conversation_commands` 的独立 intent_index 3，记录原 message 及逐字 quote。保存 `onboarding_state.operating_direction` 的原文和来源，创建真实 config revision 并发 owner_direction 事实。普通查询不调度，重复消息不重复转交。指令不恢复暂停状态，也不修改 Goal 或授予能力。决策准入核对冻结的 config revision，防止新输入后旧提案生效。

config、偏好、Goal 与经营指令由同一条 SQL 取得。等待精确 Task/generation 时，原任务与原决策无论先后完成，都只产生一次 `work_settled` 事实，不记为新证据或业务进展。未绑定的完成不额外唤醒。重复空发现不承诺新的健康等待，重复回读仅改名称、去重标记或期限仍复用同一 Task；实际清洗后的观测或原实验复盘窗口允许新一次回读。
