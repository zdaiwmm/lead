# Lead 局部故障隔离实施记录

2026-11-11。承接 `SYSTEM_COUPLING_AUDIT_20261111.md`，用户已授权实施。基于工作区当时的未提交版本增量修改，原有改动已保留；未提交、推送或发布生产。

## 实现结果

| 原审计项 | 已实现的行为 |
| --- | --- |
| F01 连续失败全局暂停 | 失败计数、冷却和提示按工作类别保存，不修改用户选择的运行/暂停状态。对话失败提供现有重试入口；发布和规划沿用各自的重试机制。 |
| F02 额度超限全局暂停 | 结算保留真实超额和未知费用预留，额度不足只限制新模型调用，不暂停 Agent。 |
| F03 统计、复盘、计划阻挡执行 | 将可选复盘、计划、进度汇总、后续建议和发布统计包在独立保存点中；SQL 失败会先回滚其保存点，再保留局部故障，不回滚已完成工作。可选查询有超时和冷却。 |
| F04 配置及账号连锁失效 | 换号创建独立账号记录，旧账号、授权、群关系和回执保留。归因和推广链接变化不再增加全局内容版本；链接变化只撤回尚未提交的关联发布。实际业务资料、品牌与内容偏好的变化仍保留内容版本检查。 |
| F05 一条坏事件阻塞派发 | 普通事件增加租约、逐条错误记录和退避；独立任务并发派发，对话信号保持顺序；RPC 有时间上限，工作流 ID 继续防重。归档 Agent 的旧事件不挤占活跃任务的优先位置。 |
| F06 辅助服务影响业务派发 | 分析采集、通知收集、外部通知投递、经验汇总分别运行；失败和重试不再共用业务派发的成败边界。分析派发的数据库操作移出事件循环。 |
| F07 只读动作依赖备份新鲜度 | 浏览器门禁区分只读与提交；找群、读消息和回执读取可跳过发布备份新鲜度检查。写入、身份和恢复隔离检查继续保留。 |
| F08 真人验证暂停所有工作 | 验证等待只排除依赖该浏览器的候选工作，内容等独立工作仍可选择；换号/解绑时归档旧账号的验证等待，避免它挡住新身份。 |
| F09 单帖分发状态污染渠道能力 | 审核中、私密、拒绝等状态绑定原帖子并单独提示，不清空已验证的整个渠道发布能力。未通过的首次能力验证仍不能凭空获得能力。 |
| F10 工作台和聊天依赖统计 | 聊天使用有界消息上下文并跳过统计；工作台列表和详情的统计可降级。新增轻量状态接口，故障显示不依赖统计或完整工作台数据。列表、连接状态、详情分别更新。 |
| F11 所有服务共用启动前提 | 按服务检查实际依赖：Web 不再检查浏览器、备份或 Temporal；API 不再要求 Temporal 和浏览器资料卷；执行器仍检查自己所需的连接。 |
| F12 执行容量相互挤占 | 相同 Agent 不同工作类别可分别占用执行名额；聊天和发布使用现有进程内的独立活动队列与预留容量。旧工作流通过版本标记兼容重放。 |
| F13 备稿绑定账号 | 待连接渠道也可准备文案；换号不改变内容版本，素材制作不受无关控制版本变化影响。确认未发送的库存可回到待发布状态，有已提交/未知回执的内容不回收重发。 |
| F14 短链成为发布前提 | 普通推广可使用有效的公开业务链接；无链接原生内容可继续保留唯一操作标记。明确要求可归因短链点击的任务仍保留相应前提，不伪装成可测量结果。 |
| F15 人数查询失败阻塞六小时 | 保存上次成功人数和时间，另记失败及短期复查时间；未知人数不当成零人，也不当成发布权限。 |
| F16 读取通知触发全量收集 | 通知接口只读已有事实；收集和外部投递在后台分开完成。单 Agent 的通知计算失败不会回滚其他 Agent 的通知。 |
| F17 静音被当成恢复 | 故障事实与通知静音分别保存；静音不写恢复时间。同一故障的说明、严重程度可更新；安静时段只延迟外部投递，站内故障立即可见。 |
| F18 故障更新不及时 | 事务内记录轻量界面版本，任务结果内容和故障变化均触发刷新；移除每连接每秒多表统计扫描。读取请求有五秒期限，保留上次数据并提示未更新；通知响应变更事件且有十五秒轮询后备。 |
| F19 心跳冒充业务进展 | 页面明确显示“执行器在线”；故障有范围、原因、首次/最近时间、处理需求和重试时间。轻量状态接口提供实际任务完成记录，排除调度决策。去掉未经证实的“其他工作正在继续”文案。 |
| 实施中补发现 F20 | 通知组件在登录完成前请求会收到 401，并可能让整页回到登录页。通知现在等待工作区会话就绪，独立加载失败只显示通知未更新。已用全新浏览器会话复现并验证。 |

## 保留的边界

- 用户主动暂停、工作时段、预算预留、租户权限和外部提交前的身份检查继续有效。
- 外部结果不明的动作保留原任务与回执，只核对，不因为换号生成新的发送副本。
- 同一浏览器会话的操作仍串行。正在进行的长调研有时限；预留容量保证聊天和已排队发布可以继续，并不声称所有渠道能同时操纵同一个浏览器。
- 数据库、实际执行资源和目标平台权限仍是对应动作的必要前提。本次没有引入新的外部基础服务。

新增迁移 `0030_fault_isolation`：保存局部故障和轻量界面版本，为通知增加静音及独立外部投递状态。表继承租户、Agent 和成员访问限制。

正式回归覆盖保存点回滚、换号归档、迟到登录验证、坏事件和慢事件隔离、未知回执防重、无账号备稿、静音与恢复、通知投递失败、受众查询失败以及轻量状态读取。真实 Temporal 验证包括故障恢复、历史重放和调研占满名额时聊天/发布仍可运行。

桌面与 390px 手机界面已检查；故意让健康检查失败后，原工作与故障信息保留，页面显示未更新提示；没有页面脚本错误和手机横向溢出。

## 启用顺序

1. 在目标环境备份并执行到 `0030_fault_isolation` 的迁移；迁移可在旧应用运行时完成。
2. 启动新执行器，确认它监听原 `lead` 及 `lead-chat`、`lead-publish` 活动队列，再更新 API/Web。
3. 核对局部故障、通知和已有未知回执的读回结果，再观察实际任务进展。
4. 回退时应先保留新活动队列的消费者直至其已排队活动完成；不能只启动不认识新队列的旧执行器，否则新队列活动会等待。保留新增表和历史，不执行破坏性降级。

这些是交付后的启用步骤；当前没有执行生产部署。
