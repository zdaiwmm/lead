## 已确认的耦合

优先级说明：P1 会扩大故障影响范围或长期中断有效工作，应优先修复；P2 造成额外等待、无关重算或恢复困难，应随架构调整处理。本次没有足够证据判定线上发生了数据破坏级 P0 故障。

### F01 聊天或单类执行失败可以暂停整个 Agent

**P1；已离线复现。**

`admin_operations.failure()` 只按 Agent 和 category 计数，达到阈值后写入整个 Agent 的 `desired_state='paused'`，并增加全局控制版本。`activities.chat_job()` 在模型请求失败、限流或认证失败时调用它；规划和发布也调用同一机制。

这意味着聊天模型连续失败，即使已有内容、其他渠道和浏览器正常，后台运营也会停。自动故障和用户主动暂停还共用同一个状态，服务恢复后无法简单判断是否应该自动继续。

证据：`admin_operations.py:98`、`activities.py:359`、`activities.py:410`、`activities.py:817`、`activities.py:1278`。复现 `chat_failure_global_pause` 在阈值为 5 时观察到全局暂停更新。

**整改：** 用户的运行意愿与实际模块健康状态分开保存。按模型、渠道、目标或动作类型记录冷却和待处理原因，达到阈值只暂缓相关工作；依赖恢复后自动重新检查。用户主动暂停仍保留最高优先级。

### F02 模型费用超限停止不需要模型的工作

**P1；已离线复现。**

`budget.settle()` 在累计实际用量超过额度时直接暂停整个 Agent。另一方面，`operating_admission.assess()` 已将回执核对、部分发布和本地准备识别为无需模型的工作。全局暂停覆盖了这一隔离。

证据：`budget.py:199`、`budget.py:257`、`operating_admission.py:68`。复现 `token_overrun_global_pause`；对照 `positive_free_work_admission` 证明零可用 token 且模型不可用时，回执核对本身仍能通过候选准入。

**整改：** 额度限制只拦截新的付费调用，保留真实用量与未知扣费预留；已生成文案、回执核对、本地整理和查看继续执行。额度恢复或下一个周期到来时自动唤醒付费工作。不能通过忽略未知费用来伪造余额。

### F03 统计反馈和计划同步成为每轮执行的硬依赖

**P1；计划失败已离线复现，其余按调用链确认。**

`operating_kernel.candidates()` 必须先执行 `review()`，后者直接读取 `metrics()`。`cycle.prepare()` 在确定任务后还要同步周／日计划并取完整计划引用，才能执行任何候选。以上过程位于执行分支的异常隔离之外。

结束阶段，业务进度汇总、Agent 调度状态、决策完成记录以及再次同步计划共用同一个数据库事务。末尾汇总或计划异常会使该事务回滚；外部动作已经发生时，仍需要靠各自的动作账本恢复，不能依靠本轮决策已完成来判断。

证据：`operating_kernel.py:103`、`operating_kernel.py:740`、`operating_kernel.py:777`、`operating_kernel.py:982`；`operating_feedback.py:128`；`operating_plans.py:989`。复现 `plan_sync_blocks_execution`。

**整改：** 区分决定任务合法性的业务策略与用于展示和优化的派生计划。已获准任务可以使用最后有效策略继续；统计过期时标明未知或过期。派生汇总异步更新，失败不回滚核心任务状态。不存在有效业务策略时才等待必要资料，不能把无效策略当作可用默认值。

### F04 无关配置变更取消整批排队任务

**P1；配置快照行为已离线复现。**

`snapshot_preferences()` 增加统一配置版本，并取消当前 Agent 下全部 `planned/queued` 任务，没有按任务类型或实际依赖筛选。修改推广链接、发布归因配置也会走这个入口。账号替换还增加统一控制／授权版本，研究和素材等任务也检查这些版本。

这里的 SQL 受 Agent 数据范围限制，不是取消全数据库所有租户的任务；但对一个 Agent 内的不同模块仍过宽。

证据：`domain.py:834`、`analytics.py:99`、`admin_operations.py:53`、`channels.py:88`、`operating_kernel.py:551`。复现 `config_cancels_all_queued_types`。

**整改：** 任务只记录它实际依赖的业务、品牌、内容、链接、账号和授权版本。修改链接只重建含旧链接的发送计划，公开研究结果和不含链接的素材仍保留。账号变化只使原身份执行失效，不使业务资产失效。旧数据保留来源，不能就地改成新账号的历史。

### F05 一条失败事件阻塞同工作室后续派发

**P1；已离线复现。**

普通待派发事件按时间取前 50 条。`deliver_workspace()` 逐条处理，除特定重复工作流情形外没有逐事件异常隔离。前面的坏载荷或特定事件的持续派发失败会直接退出本轮，后面的有效事件无法被处理；上层退避作用于整个工作室。

证据：`worker.py:61`、`worker.py:76`、`worker.py:209`。复现 `outbox_poison_event`：第一条缺少 job_id，第二条属于另一 Agent 的正常聊天事件也未派发。不同工作室已有异常隔离，不能描述成所有租户必然一起停。

**整改：** 每条事件独立记录尝试次数、下次执行时间和错误；隔离坏事件并继续无关 Agent 的事件。维持同一业务对象必要的顺序，保留幂等派发与成功确认，不把失败事件直接丢弃或标为成功。

### F06 统计和通知故障共用业务派发的退避范围

**P1，统计路径有配置前提；已离线复现。**

未设置 `LEAD_ANALYTICS_DEDICATED=1` 时，`deliver_workspace()` 在读取业务事件前等待全部统计派发与汇总。统计异常会使本次业务派发根本没有开始。通知收集和经验收集则在业务派发之后，但仍位于同一工作室的异常处理内；失败会给下一轮业务派发施加同一个退避。

已有独立统计队列、独立统计进程选项和独立外部通知发送任务，这是可复用的基础。本次没有核验线上开关，因此不能断言当前线上一定走统计共用路径。

证据：`worker.py:76`、`worker.py:180`、`worker.py:195`；`analytics_delivery.py:99`。复现 `analytics_blocks_business_dispatch`。

**整改：** 业务派发、统计刷新、通知收集、经验总结分别拥有异常边界、时限和退避。通知损坏只产生通知待修复状态，不能推迟发布和聊天任务。

### F07 备份新鲜度被用作浏览器通用操作门禁

**P1；已离线复现。**

生产模式下 `Actor.gate()` 要求本地与异地备份均就绪。迁移中这两个检查均使用 15 分钟新鲜度阈值。备份上传或校验延迟因此可能阻止正常操作；部分社群读取也通过同一个 gate，影响不止新发布。浏览器备份锁另按 Agent 挡住浏览器启动和使用。

证据：`browser.py:368`、`community_runtime.py:211`、`community_runtime.py:248`；`0006_telemetry.py:24`、`0007_operations.py:14`。复现 `backup_freshness_blocks_browser_gate`。

**整改：** 把“当前任务账本能否可靠写入”与“异地备份是否落后”分开。前者确实失败时停止产生外部副作用；后者进入明确的告警和备份恢复流程。纯读取、查看与恢复核对不应复用发布门禁。备份锁只覆盖需要一致快照的具体资源和短窗口，相关容灾要求仍应在改动中明确保留。

### F08 单个浏览器验证待办让整个调度提前退出

**P1；已离线复现。**

上一轮检查还低估了影响范围：不只是发布目标被挡住。`cycle.prepare()` 一发现待验证状态就返回，连内容、计划以外的本地整理等非浏览器候选都不再选择，返回等待 3600 秒。浏览器网关也按 Agent 检查同一待办；打开另一平台时会要求先完成旧平台的验证。

证据：`operating_kernel.py:748`、`browser.py:1022`、`browser.py:1633`；`browser_challenges.py:22`。复现 `challenge_stops_all_candidate_selection`。

**整改：** 验证待办归属具体账号和浏览器会话；真正需要这个会话的任务等待，其他任务继续。需要换号时封存旧身份任务并启用新身份，不要求新任务先完成旧账号验证。平台本人验证仍需本人完成，不能把“解除全局阻塞”实现为跳过平台验证。

### F09 一条内容未公开或被拒绝使整个发布目标失去能力

**P1；已离线复现。**

`publication_delivery.persist()` 把该目标所有非 public 的已确认提交都作为 pending，范围包含 rejected、private 等状态。一旦存在这种记录，就清空整个目标的 `publishing_verified_formats`。发布候选又要求这些格式非空。

因此一条被拒绝的 TikTok 内容，即使其他内容可发，也会阻止这个目标安排后续正式发布；拒绝状态长期不变时会长期存在。影响范围是该发布目标，不是全部平台。

证据：`publication_delivery.py:36`、`publication_delivery.py:101`、`publication_delivery.py:132`；`operating_kernel.py:88`。复现 `rejected_post_disables_target`。

**整改：** 分开保存适配器技术能力、账号能否发布、单帖是否公开。单帖拒绝进入终态或内容修订任务，不清空账号能力。只有获得账号级限制证据才暂停该账号；首帖能力尚未验证的情况单独处理。

### F10 统计与完整详情故障影响列表 页面和聊天

**P1；聊天路径已离线复现。**

Agent 列表对每个 Agent 同步读取指标，一项失败会使整个列表接口失败。详情把消息、账号、任务、素材、统计与运营摘要放进同一个请求。`chat_job()` 在进入自己的异常处理前先读取完整详情；统计出错时，聊天尚未处理用户文本就抛错。

前端刷新又把账号列表和健康接口放在同一个 `Promise.all`，成功后才读取详情。健康接口本身已捕获常见数据库和浏览器失败，因而不能把每次浏览器离线都说成页面必然失败；剩余问题是接口或聚合依赖出错时仍整体失败。

证据：`domain.py:276`、`domain.py:293`、`domain.py:378`；`activities.py:75`；`apps/web/app/page.tsx:97`。复现 `chat_requires_full_detail`：详情依赖抛错后仅留下 processing 更新，未进入聊天内部的错误处理。

**整改：** 聊天只读取必要对话与业务资料；控制指令不依赖统计。列表和详情中的统计、进度、健康等可选区块分别加载，失败时保留可用部分并显示过期状态。涉及身份和租户权限的错误不能当成可选区块失败忽略。

### F11 所有正式服务共用与自身无关的启动前提

**P2；按代码和 systemd 入口确认，未重启服务验证。**

`scripts/service.py` 在选择启动 web、API、worker、analytics 或 maintenance 之前统一运行 `preflight()`。其中包含 Temporal 连接配置、备份目标与密钥路径、浏览器登录资料加密卷等校验。因此，即使只是重启网页界面，也可能被任务服务证书文件或浏览器卷检查挡住。

证据：`scripts/service.py:13`、`scripts/service.py:36`；`infra/systemd/lead@.service:15`。

**整改：** 按服务职责声明必需配置。网页只需自身运行条件，worker 检查任务服务与数据库，备份服务检查备份目标，浏览器检查登录资料存储。公共身份和网络访问约束保留，减少无关服务之间的启动依赖。

### F12 长任务占住 Agent 执行名额 共享资源放大延迟

**P2；串行依赖已确认，实际饥饿和压力程度待运行验证。**

调度每轮只执行一个候选，并等待其完成；公开社群发现可等待约 600 秒。`managed_execution` 持有并续租 Agent 执行名额，`admission()` 对同一 Agent 的其他类别也拒绝准入，因此研究执行期间，新发布可能一直 deferred。聊天、调度和发布又共用 lead 工作队列的活动名额。

浏览器 actor 和锁按 Agent 建立，公开研究命令也取得同一个 actor 锁。部分提交还在持有 Agent 数据库行锁的事务内等待浏览器 I/O。线程池和数据库连接池有上限，但多个类别共用容量；单个慢步骤有可能进一步扩大延迟，需要注入慢操作确认实际排队行为。

证据：`operating_kernel.py:921`、`operating_kernel.py:950`；`admin_operations.py:155`、`admin_operations.py:185`、`admin_operations.py:254`；`worker.py:236`；`browser.py:774`；`research.py:329`；`db_pool.py:18`、`async_db.py:12`。

**整改：** 调度只选取并派发可执行步骤，长研究和素材任务独立执行；真正共享浏览器的操作仍互斥，控制和回执恢复保留容量。把长任务拆成短步骤、检查点和可恢复等待。移出数据库事务中的慢 I/O 时，必须保留提交前身份与撤权检查的正确性，不能简单删除锁。

### F13 未发送内容的生产和复用仍绑定不必要的账号状态

**P2；按查询和版本检查确认。**

`content_backlog.reserve()` 仅针对已连接且自动化开启、但尚无可发布目标的账号生成库存；没登录时，这条备稿路径不运行。库存查询又严格要求统一配置版本一致。素材生产的 `current_guard()` 同时检查 Agent 控制版本，因此换账号等操作会让本来不使用账号的制作任务失效。

证据：`content_backlog.py:27`、`content_backlog.py:37`、`content_backlog.py:57`、`content_backlog.py:142`；`creative_pipeline.py:85`。

这不是说系统所有离线工作都依赖登录：通用渠道底稿 `kits` 已可独立准备。但可直接用于发布的内容库存还没有彻底做到资产与执行身份分开。

**整改：** 依据已选择的渠道与业务策略准备内容，登录只是发送的必要条件。素材保存业务与品牌来源；发出时才绑定实际账号和目标，并校验内容适用性。品牌事实变化时重审相关内容，账号更换不应强制重做内容。

## 应保留并推广的隔离

1. `operating_admission.assess()` 区分付费与无需模型的工作；模型本身已有超时、调用上限和模型相关退避。应修复上层全局暂停覆盖，而非另建一套费用系统。
2. `assets` 和 `creative_pipeline` 使用有时限的子进程，失败回收子进程，制作任务有独立状态；可选渠道头像制作失败已有继续发布的处理。
3. `telegram_inbox.cycle()` 在内部处理失败后返回 None，让其他工作继续；同类边界应覆盖其执行前的依赖读取。
4. `maintenance` 的备份、监控、统计清理、分发复查和进度维护各有循环及错误处理，不因普通单项异常结束整个维护循环。
5. 分析采集已有独立任务队列、逐事件租约和延迟重试，可以复用到普通业务派发；旧 `collector_gateway` 导入整个 API 的部署方式是否仍在使用需核验。
6. 外部提交先记录意图、已确认回执保护和旧身份未知动作排除已有实现。`execute_task()` 在 RPC 出错后会读取动作账本；已确认动作不会仅因事后链接核对失败就被自动当作未发送。不能为了简化而破坏这些正确行为。
7. 数据库不可写、租户身份不可验证、目标或账号身份不明、用户主动暂停以及原发送结果未知，确实需要限制相关动作。整改目标是限制准确归属的动作，而非在所有错误情况下继续产生外部副作用。

## 统一整改规则

不必先拆成大量微服务，也不需要再加一套覆盖所有模块的审批系统。首先把现有模块的依赖与失败范围限定清楚：

| 层次 | 必需依赖 | 失败后仍应能做什么 |
| --- | --- | --- |
| 用户运行设置 | 用户保存的启用范围与明确暂停状态 | 故障不改写用户的运行意愿 |
| 资料与内容资产 | 业务、品牌、内容来源 | 未登录时仍能整理资料、备稿和制作适用素材 |
| 单个执行步骤 | 本步骤需要的账号、目标、浏览器、模型或媒体 | 只把该步骤标记为等待、失败、结果未知或完成 |
| 调度与队列 | 可执行步骤、时间与必要资源名额 | 跳过暂不可执行的步骤，派发无关工作 |
| 历史与回执 | 当时实际身份、目标、提交事实 | 封存旧身份任务，保留去重证据，新任务继续 |
| 统计、计划展示与通知 | 核心事实的派生结果 | 缺失时标记未知／过期，后续补算，不回滚执行事实 |

等待记录只需表达具体依赖、原因、下次检查或唤醒条件；可以在现有任务与状态表内实现。不要再用单个 `needs_attention` 或全局版本同时代表所有模块的状态。

## 建议实施顺序与验收

以下是本次审计后的实施顺序，尚未进行业务代码修改。

**第一批：故障可见与运行隔离一起交付。** 修复 F01、F02、F03、F05、F06、F10，并把 F08 中非浏览器任务的调度阻断移除；同时完成 F16—F19 的故障状态、通知读取、恢复说明和界面过期提示。不能先让错误被跳过、以后再补用户反馈。保留用户主动暂停语义；错误按模块或对象保存。

**第二批：删除软前提并分离资产与执行。** 修复 F04、F09、F13—F15，统一账号替换和旧任务封存。先建立新旧身份可区分的数据结构，再切换读写，保留原始回执和来源；不批量篡改旧任务身份或把未知发送改成未发送。效果测量不可用时，按明确的降级策略执行并显示数据缺口。

**第三批：缩小基础设施与资源故障范围。** 修复 F07、F11、F12，按职责拆启动前提、备份告警、执行名额和浏览器资源；维持现有安全边界并验证并发正确性。

| 注入条件 | 必须继续的工作 | 必须限制的工作 | 恢复要求 |
| --- | --- | --- | --- |
| 聊天模型连续限流 | 其他模型任务、库存发布、回执核对 | 对该模型的新调用 | 冷却结束自动重试，不要求恢复整个 Agent |
| token 预算耗尽 | 无付费依赖的核对、本地处理、适用库存发布 | 新付费调用 | 周期刷新或额度增加后恢复 |
| 统计查询或周计划汇总抛错 | 已授权且依据有效策略的任务、聊天和基本工作台 | 依赖新统计才能做出的优化决策 | 补算并标记数据时效 |
| 队首坏事件 | 同工作室其他 Agent 和无顺序依赖的事件 | 该坏事件及真正依赖它的后继 | 逐事件重试和可见错误 |
| 通知服务失败 | 任务派发与业务执行 | 对应通知交付 | 恢复后补送并去重 |
| 更改推广链接 | 无关研究、素材与不含旧链接的任务 | 使用过期链接的发送 | 只重建相关发送任务 |
| 旧账号仍有结果未知任务时换号 | 新身份的新任务、可复用内容 | 原未知动作的盲目重复发送 | 原动作封存，旧身份恢复后按原记录核对 |
| 单浏览器等待真人验证 | 无关浏览器与不需要浏览器的任务 | 依赖该验证会话的操作 | 完成后仅唤醒关联任务 |
| 单条 TikTok 内容被拒绝 | 账号仍有权限时的新内容任务 | 原拒绝帖的无条件重发 | 帖子终态不永久污染账号能力 |
| 素材子进程崩溃 | 其他素材任务及支持文字格式的任务 | 依赖该素材的发送 | 有界重试，不伪造制作成功 |
| 异地备份短时延迟 | 查看、研究、可可靠记账的授权业务 | 无可靠本地账本的外部副作用 | 告警与备份恢复独立完成 |
| 长研究或浏览器慢操作 | 无关控制、其他渠道、回执恢复 | 同一浏览器上冲突的操作 | 短步骤和公平排队，名额最终释放 |

交付时至少连续运行三轮多任务混合流程，并在运行中注入上述故障、恢复依赖，再验证一次重启恢复；三轮只是冒烟门槛，还需要覆盖一个完整日周期、额度刷新、排期、登录变化及备份周期。每轮必须记录：应执行工作、实际完成或等待原因、故障影响范围、恢复耗时、是否发生重复外部提交。进程在线、测试通过和调度决策成功均不能替代实际任务闭环。

## 方案复核与反馈闭环

### F14 推广短链配置阻塞整个正式发布候选

**P1；按代码确认。**

`activities._publication_cycle()` 在规划内容之前检查 `configured_problem()`，非 lab 的目标只要没有合法公网 HTTPS 短链配置就被全部排除。`promotion_body()` 又强制把产品链接替换为短链。当前依赖是“短链配置有效”，并非证明每次都检查远端短链服务存活；不能把两者混为一谈。

社群普通帮助已有较窄边界：只有 `decision.promote` 时才要求短链。但自有渠道正常发文的边界仍过宽。公开可访问的业务原始链接存在时，无法计量点击不等于无法发布。

证据：`activities.py:1083`、`promotion.py:129`、`promotion.py:154`、`community_runtime.py:2554`、`outbound_links.py:29`。

**整改：** 在形成发布内容后判断该任务是否需要链接。无链接内容不依赖短链；有合规业务目标链接时允许直接链接或目标支持的轻量来源参数，显示“已发布，点击归因暂不可用”。用户明确要求必须可归因的试验仍等待测量恢复。不能擅自删掉用户要求的行动入口、把内网地址发出去，或把归因缺失统计成零点击。

### F15 受众人数读取失败被当成六小时内有效的发布否决条件

**P2；已离线复现。**

`owned_audience.inspect()` 捕获 HTTP 异常后仍保存 `count=None` 和新的 checked_at，返回六小时等待。`status()` 在六小时内返回 unknown。启用 first_users 或 chamber_first_users 策略时，调度与发布入口又要求 audience 为 eligible，因此一次读取失败会阻止该目标发布至下一次到期复查。

证据：`owned_audience.py:10`、`owned_audience.py:29`、`operating_kernel.py:376`、`activities.py:998`、`growth_experiments.py:26`。复现 `audience_network_failure_suppresses_target_six_hours`。

**整改：** 读取失败与确认为空分开。保留最后一次成功观测，失败只更新失败时间与短退避；“未知”不能自动等于“没人”。人数用于投入排序，不能替代真实发布权限。确认为空且策略要求优先外部获客时仍可降低发布优先级，但界面应解释这是策略等待。

### F16 读取和保存站内通知仍依赖故障收集及外部交付

**P1；已离线复现两条路径。**

通知列表 GET 先调用完整的 `collect()`，然后才读取已有通知。收集读取额度、运行配置、品牌和归因等数据，而且主循环所有 Agent 共用一个事务；其中一项异常可以阻止保存和读取其他正常通知。

`condition()` 新建站内通知后，在同一事务内调用外部交付 `enqueue()`，读取并使用外部通知配置。外部交付配置或入队异常会向上传播，使站内记录也不能提交。真正发送邮件或 webhook 已异步执行，但入队仍未隔离。

证据：`admin_api.py:537`、`admin_notifications.py:107`、`admin_notifications.py:90`、`admin_delivery.py:198`。复现 `notification_read_requires_collection`、`external_delivery_enqueue_breaks_local_notification`。

**整改：** 通知读取只读取已提交的状态，不运行全量收集。执行步骤直接保存简短故障事实；收集器负责补漏，每个 Agent 或故障独立处理。站内记录先完成，外部交付在独立事务中根据记录生成，维持去重。外部通道失败只影响外部送达，不影响站内显示和业务任务完成。

### F17 故障状态与通知偏好混为一体 导致假恢复和信息过时

**P1；已离线复现三种行为。**

`condition()` 用 active、通知开关和类别筛选共同计算 should_notify，再把它写成故障条件的 active。即使真实故障仍存在，关闭提醒也会给原通知写 resolved_at；通知界面将它显示为“已恢复”。同一 episode 仍 active 时，不刷新通知标题、正文和严重程度，影响范围扩大也可能继续展示旧信息。

普通通知的免打扰通过延后 available_at 实现；站内 visible 查询也按该字段过滤。因此免打扰不仅不主动打扰，还会使用户主动打开通知时看不到新故障。复现场景为凌晨 00:30 的普通故障被隐藏到 08:00。

证据：`admin_notifications.py:13`、`admin_notifications.py:51`、`admin_notifications.py:245`；`apps/web/app/admin/operational-settings.tsx:910`。复现 `muting_resolves_active_fault_notice`、`active_episode_does_not_refresh_details`、`quiet_hours_delay_in_app_visibility`。

**整改：** 实际故障、已读、静音、免打扰和外部送达分开保存。静音或已读不改变故障是否存在；免打扰只抑制弹出或外发，当前故障状态持续可查。持续故障更新现有记录而非刷屏；需要用户处理或影响扩大时适度升级。只有关联依赖核验恢复或原任务被明确封存／取消才结束故障，封存不冒充恢复。

### F18 实时刷新遗漏故障变化 刷新失败也缺少过期提示

**P2；SSE 变化检测已离线复现，其余按界面代码确认。**

SSE revision 读取 Agent 部分字段、任务状态计数和活动记录等聚合，但不包含通知或任务结果中的局部故障详情。只有这些详情改变、状态计数没变且没有其他可观察变更时，不触发对应刷新。通知角标单独每 30 秒读取，未订阅这类变化。

工作台每 15 秒轮询，异常被静默忽略；基本刷新请求没有整体截止时间，polling 标志在一次请求悬挂时可长期阻止后续轮询。通知读取失败则去掉计数，未区分“没有通知”和“当前无法获取通知”的可见状态。

此外，每个 SSE 连接每轮执行多项全工作室聚合；每次触发又刷新列表及完整详情。已有列表 N+1 指标查询和详情全量消息读取，会随 Agent、历史与在线窗口增加放大开销。这里确认的是查询结构，尚未测量实际性能瓶颈。

证据：`events.py:18`、`events.py:57`；`apps/web/app/page.tsx:145`、`apps/web/app/api-client.ts:17`、`apps/web/app/notification-indicator.tsx:9`；`domain.py:276`、`domain.py:293`。复现 `event_revision_omits_notification_and_issue_details`。

**整改：** 只为状态变化维护轻量版本或事件序号，SSE 提示具体对象已变化，读取对应卡片的最新状态；保留低频兜底查询。基本状态请求有明确截止时间和单次在途限制；失败时显示最后更新时间与“状态暂时无法刷新”，不保留毫无提示的绿色旧状态。仍须正常执行租户／成员权限检查，切换工作室后清除旧范围缓存。

### F19 存活 调度完成和业务进展混用 故障说明缺少依据

**P1；已离线复现两条路径。**

工作室派发失败被捕获后，worker 仍更新心跳。该心跳只证明派发循环存活；API 健康状态把它用于 worker 在线显示，不能据此证明任务在执行。内部 ops 告警有队列老化检查，但它不是普通用户可直接读取的局部故障面板。

调度捕获执行异常后记录通用 `lane_temporarily_unavailable` 和异常类型，之后仍将 operating.decision 标为 succeeded。调度器完成一次决策本身并不错误，但不能把它当成业务成功。界面 `blocked_reason()` 优先返回通用 reason，可能忽略更具体的 TimeoutError；默认文案直接说“其他独立工作继续”，却没有附带实际已推进工作的证据。

通知收集主要覆盖七类固定状态。模型冷却、素材失败、局部短链阻塞、派发坏事件、计划汇总异常、浏览器验证等并不都进入统一通知；部分有活动、聊天消息或专门卡片，缺的是一致的局部范围、处理方式、下次检查和恢复反馈。Agent 级 category key 还会合并不同账号的同类问题。

证据：`worker.py:204`、`api.py:688`、`ops.py:153`、`operating_kernel.py:950`、`operating_kernel.py:1018`、`operating_plans.py:84`、`admin_notifications.py:157`。复现 `worker_heartbeat_survives_all_dispatch_failure`、`generic_reason_hides_specific_cause`。

Telegram 群卡片已有最近有效进展与局部阻塞信息，`community_health` 与 `community_progress` 也已有按账号／群保存的失败和复查机制。这些应复用并规范到其他模块，不需要重新造一个全面监控系统。

## 复核后的最小实现方案

### 方案取舍

| 选择 | 代价与局限 | 本项目判断 |
| --- | --- | --- |
| 继续逐处加例外和重试 | 单次修改小，但状态含义仍冲突，换场景再次阻塞 | 不宜作为总体方案 |
| 在现有服务内统一局部失败语义 删除软前提 | 可复用现有表、队列、通知与恢复机制；需跨模块回归 | 当前首选 |
| 全面拆微服务或建立通用依赖引擎 | 新增部署、通信、一致性、运维依赖，迁移范围大 | 暂不采用；仅在容量证据支持时拆必要执行资源 |

当前方案的优势来自减少必经调用、缩小失效范围和使用现有机制；“更流畅”的幅度仍需相同负载下的前后对照。不能用新增抽象层数或服务数证明更优。

### 六项必须落实的简化

1. **调度不等待优化结果。** 必要业务策略保存后，步骤即可根据明确的直接条件运行。统计、计划展示、通知、经验总结和效果优化异步完成；可选模块尚未成功也不影响必要任务完成记录。
2. **每步只检查自身真正需要的能力。** 备稿不检查登录，文字发送不检查视频制作，读取不检查发帖格式，直接链接发送不强制短链，换账号不废弃业务资产。检查放到第一次实际需要时；身份、目标、授权与幂等性仍在外部提交前重新核实。
3. **按已知任务类型声明少量直接需求。** 使用现有任务入口明确需要模型、浏览器、账号、素材或测量中的哪几项，不引入任意依赖图和另一套通用编排器。新模块的失败默认局限于自身任务。
4. **复用已持久化结果。** 外部提交或耗费较大的步骤保留必要检查点，恢复从最后有效结果继续。每个普通函数不都落库；避免为追踪而增加大量同步写入。
5. **一次事实记录 支撑运行和用户反馈。** 在现有任务结果／已具备范围的健康记录中统一原因码、资源范围、首次与最近发生时间、下次复查、是否需用户操作和证据引用。活动、卡片和通知从这些事实派生，不各自推断另一个“是否故障”。若现有表不足，只扩展必要字段，不新增故障服务。
6. **读取轻量状态并限制重试。** 单个步骤拥有主要重试预算，客户端、队列与执行器不能各自无界重试；瞬时失败短退避，永久配置错误等待条件变化。SSE 加轻量读取与低频兜底；数据库不可用时界面明确表示状态未知，不能承诺服务器仍能写入通知。

### 对首轮建议的必要收紧

- **拆版本也要适度。** 不为每个小字段加一套版本和授权。记录任务实际依赖的输入；账号身份和用户停止控制必须独立，内容只关心相关业务／品牌变化。最终提交前重查必要权限。
- **移出派生处理需要事务边界。** 仅在同一事务里 try/except 吞掉统计 SQL 错误不构成隔离；派生读写应在独立事务、明确保存点或提交后任务中处理。核心动作账本不可持久化时仍停止外部提交。
- **先恢复隔离 再增加并行。** 在账号身份、浏览器互斥、幂等提交尚未明确前扩大并发会造成串号或重复操作。先让等待释放资源、长步骤可恢复，再按实际资源分开执行名额。
- **现有严格约束不得被静默降级。** 保留用户明确的时段、限额、权限和容灾要求。备份软故障先解除无关只读阻塞；外部写入的降级需要与现有恢复目标一致。不能仅凭“本地能写”推导出任何备份状态都可无限期继续。
- **未知发送不能靠换任务绕过。** 新账号可以开展新的工作；同一目标的同一业务发送若仍可能已完成，应保留去重关联。换任务 ID 或归档记录不改变已提交的事实。
- **故障文案不得依赖模型生成。** 采用明确原因码与模板，模型故障时反馈仍能工作；展示安全摘要，技术详情和敏感原始响应分开保存。

## 用户反馈应如何工作

### 展示内容

工作台顶部显示“正常运行”“部分工作受影响”“需要你处理”“已暂停”或“状态暂时未知”，并显示最近更新时间。受影响的渠道／任务旁出现一条简短说明，包含：

- 哪项工作受影响，以及影响几个任务；
- 原因和最后确认时间；
- 系统正在自动处理，还是确实需要用户做什么；
- 下次复查时间或明确的唤醒条件；
- 其他工作是未受影响、正在执行，还是也在等待，依据实际状态区分。

示例文案，具体数量与时间由真实状态填入：

> Telegram 账号登录已失效，2 条发送任务等待重新登录。内容准备未受此故障影响。完成登录后会自动重新检查待发任务。

> 图片制作失败，本次发送等待素材重新生成。系统将在 14:35 重试；已有文字稿可以继续使用。

> 点击统计暂不可用。帖子已确认发送，点击效果尚未核实。系统会自动恢复统计，不需要重新发送。

> 状态已 45 秒未更新，当前无法确认任务进展。正在重新连接，最后一次确认时间为 14:32。

不得用“请重新授权”“需要处理”概括所有问题。只有实际缺少用户能提供的条件时才要求操作，且直接打开对应账号或任务入口；不让用户进入开发者日志猜原因。

### 提醒和恢复规则

- 同一资源、同一原因、同一故障期间更新一条记录，累计次数；每次重试不追加一条通知。
- 持续故障的原因、影响范围、重试时间更新到原卡片；恶化为需要用户处理时提升提示。
- 短暂且自动恢复的故障可只留活动记录；当前已阻断任务或需要用户参与的故障立即可见。
- 恢复后标记“已恢复，关联任务已重新排队”或“已恢复，等待原排期”，不能把依赖恢复等同于业务已经完成。
- 已读、静音和免打扰不清除当前故障。封存旧账号时显示“旧任务已封存”，不显示虚假的“旧账号已恢复”。
- 外部通知只使用已配置且用户启用的目的地；失败不影响站内记录，不因本次审计发送任何消息。结果未知的邮件不盲目重发；支持去重的 webhook 可按明确协议有界重试，送达问题在站内可见。
- 更新故障与界面读取保持原有租户及成员可见范围，普通用户不能通过全局健康摘要看到其他工作室信息。

### 可验收的时效目标

以下是建议的验收目标，不是当前已达到的性能。时间从系统检测到并成功保存故障事实算起；外部步骤本身还必须有明确的检测超时。

| 场景 | 目标 |
| --- | --- |
| 页面在线且状态服务可用 | 局部故障及恢复状态 5 秒内更新，不等待下一轮完整运营 |
| SSE 不可用但普通请求正常 | 15 秒内兜底刷新局部状态；通知不再另等 30 秒全量收集 |
| 用户主动打开工作台 | 直接读取已保存故障及时间，不触发全量收集；参考负载下状态接口 p95 不超过 2 秒 |
| 状态请求卡住 | 单次基本状态读取建议 5 秒截止；超过两个兜底周期未成功，显示状态过期／未知 |
| 新账号登录或配置已修复 | 立即发出关联唤醒；资源可用时 30 秒内重新判断受影响任务，等待原排期则展示排期 |
| 持续失败 | 重试有上限／退避；展示下一次检查，不反复提示同一问题，也不永久无声等待 |
| 数据库或整个 API 不可用 | 前端用请求超时显示连接异常及最后更新时间；保留已有维护监控，不能承诺不存在的实时任务详情 |

### 补充验收

在首轮的混合任务和恢复验收之外，增加以下场景：

1. 故障仍存在时关闭提醒、设为已读或开启免打扰：故障卡片仍存在，不得显示已恢复。
2. 通知收集器或外部通知配置损坏：已保存的站内故障可读取，业务状态提交不回滚。
3. 同一账号故障升级、第二账号出现同类故障：影响范围和处理动作分别准确，避免 Agent 级合并掩盖情况。
4. 发布成功但点击测量不可用：发送结果保持成功，效果显示未知；不重新发帖。
5. 频道人数读取失败：保留最后成功观测，短退避后重试，不把未知变成确认无受众。
6. SSE 断开、状态接口超时和恢复：保留可用页面，及时标明过期；恢复后刷新故障状态，不需要手动刷新整个网页。
7. 所有业务派发失败但心跳正常：显示“服务在线、任务派发异常”，不能显示正常运营。
8. 正常排期、无人回复、平台审批、用户暂停：显示等待原因，不误报系统故障。

前后对照固定相同 Agent、任务和模拟外部延迟，记录无关任务等待时间 p95、故障到可见时间、恢复到重新准入时间、每轮数据库查询数、模型重复调用和重复外部提交。至少覆盖一个完整日周期，并验证跨午夜、重启、两种故障同时发生。零重复外部提交、无越权、明确用户暂停仍生效，是提速不能牺牲的验收条件。
